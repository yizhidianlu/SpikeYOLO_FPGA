## (2) FSBL DDR self-test escape hatch — YES, EXISTS + EASY TO PATCH

**FSBL recipe location:** `meta-xilinx-tools/recipes-bsp/embeddedsw/fsbl-firmware_2024.1.bbappend` (also `fsbl.bbappend`).

**Upstream source:** `Xilinx/embeddedsw` at tag `xlnx_rel_v2024.1`,
`lib/sw_apps/zynq_fsbl/src/main.c`.

**Test location** (lines 288–303):
```c
#if defined(XPAR_PS7_DDR_0_S_AXI_BASEADDR) || defined(XPAR_PS7_DDR_0_BASEADDRESS)

    /*
     * DDR Read/write test
     */
    Status = DDRInitCheck();
    if (Status == XST_FAILURE) {
        fsbl_printf(DEBUG_GENERAL,"DDR_INIT_FAIL \r\n");
        OutputStatus(DDR_INIT_FAIL);
        FsblHookFallback();      // ← this is the 0x578 hang!
    }

#endif
```

`DDRInitCheck()` writes a pattern to DDR and reads it back at multiple addresses. If any readback mismatches, FSBL falls into the hang. **Skipping this gives DRAM training a chance to complete in u-boot's later mem test instead, which has cleaner error reporting** (and Linux will just OOM if DRAM is truly broken — but if it's only one-byte-on-mixed-patterns broken, Linux may run fine for non-trivial fractions of memory).

```
PCW_UIPARAM_DDR_TRAIN_READ_GATE   : '1'      ← already on
PCW_UIPARAM_DDR_TRAIN_DATA_EYE    : '1'      ← already on

PCW_UIPARAM_DDR_USE_INTERNAL_VREF : '0'      (external VREF from DRAM_VREF pin)
PCW_UIPARAM_DDR_AL                : '0'      (additive latency 0)
PCW_UIPARAM_DDR_BUS_WIDTH         : '32 Bit' (4 byte lanes)
```

**Significant interpretation:** Since all 3 training stages are ON, ps7_init.c sets initial taps from PCW, then the DDR controller's training hardware runs at every cold boot and **OVERWRITES the static slave-tap values based on what it measures from the chip**. So the per-byte 0x612C-0x6138 DLL slave delay values I dumped above are STARTING values — the trained final values may differ.

**Direct implication for our 3 DQS_TO_CLK_DELAY iterations:** the static -0.100→0.000→-0.050 tap changes may have been mostly no-ops at runtime — the runtime trained values are what go into the read pipeline. Our debug loop has been observing what TRAINING decides, not what PCW set.

This is consistent with Main's reframe:
- "uniform OK, mixed→0xFF" can't be a static-tap-offset signature
- Training is on; static taps are just seeds
- The real failure is either training is reaching a bad answer on byte-3 (gate vs eye), OR there's a physical lane-3 issue training can't compensate for
